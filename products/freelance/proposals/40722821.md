## Proposal

On Interactive Brokers the strategy is the easy half. What costs money is the gap between what your rules say and what the API does: a partial fill, an order rejected outside regular hours, a reconnect that leaves the client thinking it is flat while the account holds a position. If the code has no memory of what it sent, the next loop sends it again.

Plan:
- Write the rules down as entry, exit, sizing and what happens when a fill is partial, before any code.
- One client order id per signal, so a restart can tell a sent order from an unsent one.
- Reconcile against IBKR positions on every start and refuse to trade until the two agree.
- Position and daily loss caps enforced in the order layer, not only in the signal.
- A week on paper with a daily log of every signal, order and fill before the live key goes in.

Deliverables: the Python bot, the rules document, the log files, and a runbook for starting, stopping and checking it.

Proof: https://davespinelli.github.io/Claude-Space/ (public backtest engine and Alpaca execution bot)
