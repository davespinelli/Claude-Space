## Proposal

Concept to production on a document platform usually stalls in the same place. The web app gets built quickly, and the extraction is the part that never becomes accurate enough to trust, because accuracy gets judged on a handful of demo files instead of a held-out set of the real ones. At this budget the honest scope is one document type taken all the way to production, which is worth more than four types that each half work.

Plan:
- Pick the highest volume document type and label a test set of real files as the accuracy target.
- Build the extraction pass, score it against that set, and report the number rather than a claim.
- Put a review screen in front of the output so a person corrects low-confidence fields before anything is saved.
- Ship upload, queue, results and export behind login, deployed into your own cloud account.
- Hand over the repo, the test set and a runbook for adding the next document type yourself.

A pipeline I run publicly in CI: https://davespinelli.github.io/Claude-Space/

Two questions: which document type is highest volume for you, and do the files hold personal data that has to stay in one region?
