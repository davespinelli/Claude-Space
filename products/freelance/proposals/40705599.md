## Proposal

Services built on relational data fail quietly. The model keeps answering and the app keeps responding long after the table behind it stopped updating, so the first sign of a broken pipeline is usually somebody asking why a figure looks stale. Watching whether the job exited cleanly does not catch that, because a job that finishes and writes nothing exits cleanly.

Plan:
- List each service, the tables it depends on, and what current and correct means for that table.
- Add freshness, row count and schema checks per table, with thresholds set from the last ninety days of actual behaviour.
- Alert on the data checks rather than exit codes, so a silent no-op still raises.
- Schedule the checks where you can see them, with a page showing last run and current state per service.
- Set a monthly window where I fix what the checks catch and report what changed.

You get the check suite, the schedule config, the status page, and a runbook naming each failure mode and its fix.

A pipeline I run publicly on GitHub Actions: https://davespinelli.github.io/Claude-Space/
