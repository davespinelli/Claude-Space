## Proposal

The word doing the work in your brief is repeatable. A one off query answers the question this week; the problem starts when the same report is rerun next month and the number moves, because the date boundaries, the exclusions or the join changed slightly. So the first thing worth writing down is the definition of each metric, not the SQL.

Plan:
- Agree each report line as a written definition: what counts, what is excluded, and which date the row belongs to.
- Write one query per report, parameterised on the date range so a rerun is a parameter change and nothing else.
- Keep shared logic in views rather than pasting it between queries, so two reports cannot drift apart.
- Check the plan on your real row counts and add the indexes needed if anything is slow.
- Include a small runner that writes each report to CSV or Excel on a schedule, if you want it unattended.

You receive the SQL files, the views, the metric definitions, and the runner script with a README.

Proof: my public repo and its daily scheduled pipeline at https://davespinelli.github.io/Claude-Space/

Two questions: which reports do you need first, and is it PostgreSQL with read access I can query directly?
