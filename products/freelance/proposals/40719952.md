## Proposal

Changing a circuit's bandwidth through a provider API is not a call that returns an answer. It is an order that provisions over seconds or minutes, and these scripts usually break on a timeout during the change call. The change may have gone through or not, the script cannot tell, and the retry either doubles the order or leaves the circuit at the wrong speed until it shows up on a bill.

Plan:
- Read your script and the API docs, and list every call needed for increase, decrease and read back.
- Handle the token properly, refreshing before expiry instead of reacting to a 401 mid run.
- Make each change idempotent: one request id per change, confirmed by reading the circuit state back.
- Poll provisioning to a final state, with a timeout and a plain failure message.
- Log every change with timestamp, old speed, new speed and outcome.

You get the script, a config file for credentials, a README, and a dry run mode that prints what it would do.

Proof: my public pipeline and dashboard at https://davespinelli.github.io/Claude-Space/
