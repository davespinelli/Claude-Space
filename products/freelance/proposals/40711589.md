## Proposal

Scheduling tools get abandoned at the same point: the generated plan puts a task somewhere the team knows is impossible, nobody can see why it did that, and everyone goes back to the spreadsheet. The value is not the generation, it is that the constraints are explicit enough that a plan can be argued with.

Plan:
- Write down the scheduling rules you actually run on: dependencies, who can do what, availability, fixed dates, and what may slip.
- Build the model as a solver over those constraints, so every placement has a reason attached.
- Use the LLM where it earns its place, reading briefs and messages into structured tasks, not deciding the dates.
- Show the plan with its reasoning: why this date, what blocks it, what moves if it slips.
- Ship it as an API plus a simple view, with the source and a README.

You get the constraint model, the scheduler, the ingest layer, the interface and the code.
