## Proposal

A single throughput figure is the least useful result a load test gives you. What you need is the point where latency turns: the rate at which p95 climbs while p50 still looks fine, and what runs out first there, connections, CPU or a pool limit. Two things quietly invalidate most results. The load generator itself becomes the bottleneck, and every virtual user replays one record, so the cache answers everything and the real path is never exercised.

Plan:
- Agree the scenarios that represent real traffic, the endpoint mix and think time.
- Build the tests in k6 or Locust, varying data per user so caching does not flatter the numbers.
- Verify the generator has headroom before trusting its numbers.
- Ramp until the latency knee appears, then hold there to see if it is stable or degrading.
- Report p50, p95, p99, error rate and the saturation point, with the first bottleneck named.

You get the scripts, the run configuration, the report and a command to repeat it after any change.
